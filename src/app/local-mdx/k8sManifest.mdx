`kubectl get pods`를 쳤더니 전부 `Running`이었다. 그런데 서비스는 응답하지 않았다.

Pod가 죽은 것도 아니고 이미지를 못 받은 것도 아니다. 두 개 다 떠 있고 상태도 정상이다. 그런데 Service를 통해 들어가면 아무것도 안 나온다.

원인은 YAML 두 파일에 적힌 이름표 한 글자였다.

## 선언

5일차는 클러스터 위에 처음으로 애플리케이션을 얹는 날이었다. Deployment로 Pod를 띄우고 Service로 통로를 낸다.

여기서 처음 나온 구분이 명령형과 선언형이다.

| | 명령형 | 선언형 |
| --- | --- | --- |
| 명령 | `kubectl run` · `kubectl create` | `kubectl apply -f` |
| 기록이 남는 곳 | 셸 히스토리 | YAML 파일 |
| 같은 걸 또 실행하면 | 이미 있다고 오류 | 파일 내용에 맞춰 준다 |
| 뭐가 바뀌었는지 | 확인할 방법이 마땅찮다 | 파일 차이로 본다 |

`kubectl run`으로 띄우면 삼 초면 뜬다. 그런데 그게 뭐였는지는 내 셸 히스토리에만 남는다.

`apply`는 파일이 곧 기록이다. 다시 적용해도 오류가 안 나고 파일에 적힌 상태로 맞춰 준다.

3일차에 K3s를 설치하면서 명령 한 줄 차이로 클러스터가 갈라졌던 걸 생각하면, "명령이 아니라 파일이 남는다"는 게 그냥 취향 문제가 아니라는 게 좀 실감이 났다.

## 이름표

Deployment YAML과 Service YAML은 서로를 모른다.

```yaml
# Deployment
spec:
  selector:
    matchLabels:
      app: market-web      # ← 내가 관리할 Pod를 고르는 조건
  template:
    metadata:
      labels:
        app: market-web    # ← 내가 만들 Pod에 붙일 이름표
```

```yaml
# Service
spec:
  selector:
    app: market-web        # ← 트래픽을 보낼 Pod를 고르는 조건
```

두 파일을 잇는 건 `app: market-web`이라는 문자열 하나뿐이다. 참조도 아니고 ID도 아니다. 그냥 같은 글자인지 비교한다.

그래서 Service의 selector를 `app: market-web-old`로 적으면 이렇게 된다.

| | Pod 상태 | Service Endpoints |
| --- | --- | --- |
| Label이 맞을 때 | `Running` | Pod IP 2개 |
| Label이 다를 때 | `Running` 그대로 | 비어 있음 |

**Pod는 아무 문제가 없다.** 죽지도 않고 경고도 안 뜬다. Service 입장에서 조건에 맞는 Pod가 하나도 없을 뿐이다.

그래서 서비스가 응답을 안 하면 `kubectl get pods`가 아니라 이걸 먼저 봐야 한다.

```bash
kubectl get endpoints market-web
```

여기가 비어 있으면 Pod 문제가 아니라 글자 문제다.

(2일차에 SSH가 멈췄을 때도 서버는 멀쩡했다. 응답이 돌아올 길이 없었을 뿐이다. 층은 다른데 모양이 같다.)

## 다시 보기

selector가 "저장된 목록"이 아니라는 것도 이날 알았다.

Service는 만들어질 때 Pod 목록을 받아 적어두는 게 아니다. 매번 Label을 다시 맞춰 본다. Pod가 새로 뜨거나 사라지면 Endpoint 목록이 그때마다 다시 계산된다.

그래서 Pod를 지웠다 다시 띄워도 Service를 건드릴 필요가 없다. 새 Pod에 같은 Label만 붙어 있으면 알아서 다시 걸린다.

부분 일치는 없다. selector에 적은 키와 값이 **전부** 맞아야 고른다. 하나라도 다르면 빠진다.

## 세 층

Deployment를 만들면 실제로는 세 층이 생긴다.

```
Deployment    배포 전략과 리비전 이력을 가진다
     ↓
ReplicaSet    replicas 수만큼 Pod가 떠 있도록 유지한다
     ↓
Pod           컨테이너를 실제로 실행한다
```

사람이 직접 다루는 건 Deployment 하나뿐이다. ReplicaSet은 Deployment가 만들고, Pod는 ReplicaSet이 만든다.

그리고 Deployment를 건드리는 방법은 여러 가지인데 결과는 두 갈래로 갈린다.

| | scale | rollout |
| --- | --- | --- |
| 바꾸는 값 | `replicas` — 몇 개 떠 있는지 | 이미지·설정 — 무엇이 떠 있는지 |
| ReplicaSet | 그대로 두고 Pod 수만 조정 | 새 ReplicaSet을 만든다 |

개수를 바꾸는 것과 내용을 바꾸는 것이 다르다는 말이 처음엔 당연하게 들렸는데, ReplicaSet 층을 보고 나서야 왜 다른지 알았다. 개수는 기존 ReplicaSet이 알아서 채우면 되고, 내용은 새 ReplicaSet을 세워야 한다.

## 되돌리기

여기서 rollback이 왜 되는지가 나온다.

배포가 끝나도 **옛 ReplicaSet이 지워지지 않는다.** Pod 수만 0으로 줄어든 채 남아 있다.

그래서 되돌리라고 하면 새로 만들 게 없다. 옛 ReplicaSet의 replicas를 다시 올리고 새 것을 0으로 내리면 끝이다.

2일차에 Swarm으로 롤백했을 때는 이게 왜 되는지 모르고 그냥 됐다. 여기서는 껍데기가 남아 있어서 되는 거였다.

다만 되돌아오는 건 Deployment 정의뿐이다. 볼륨에 쌓인 데이터는 같이 안 돌아온다. 이건 3일차에 Docker 볼륨 보면서 한 번 짚었던 것과 같은 얘기다.

닷새 동안 안 되는 걸 여러 번 만났는데, 마지막 날 것이 제일 조용했다.

NACL은 에러라도 띄웠다. K3s는 클러스터가 두 개가 되긴 했다. 이번엔 `kubectl get pods`가 전부 `Running`이라고 말해준다. 아무것도 잘못됐다고 하지 않는다.

선언형이라는 게 결국 "원하는 상태를 적어두면 알아서 맞춰준다"는 뜻인데, 내가 원하는 상태를 잘못 적으면 그 잘못된 상태에 정확히 맞춰준다. 시스템은 성실했고 틀린 건 내 파일이었다.
